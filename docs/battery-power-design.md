# Tab5 バッテリー — 充電制御・残量推定・過放電保護

`components/pwr_tab5` が何をしているか、なぜその形なのか、そして**まだ実機で
確かめていないこと**。画面の電源モデル（ACTIVE/DIMMED/SCREEN_OFF）は
[power-states.md](power-states.md) 側の担当で、本書はその下の電池そのもの。

## 1. ハードウェア

| 要素 | 実体 | 出典 |
|---|---|---|
| 電池 | NP-F550 互換 2S、7.4V / 2000mAh / 14.8Wh、着脱式 | [m5-docs Tab5](https://docs.m5stack.com/en/core/Tab5) |
| 監視 | INA226 @ **0x41**、シャント **5mΩ**、内部 I2C | M5Tab5-UserDemo `hal_esp32.cpp` / ESPHome device config |
| 充電 | IP2326、IO エキスパンダ PI4IOE5V6408 @ **0x44** でゲート | UserDemo BSP `m5stack_tab5.c` |
| 電源断 | 同エキスパンダ P4 のパルス | 同上 `bsp_generate_poweroff_signal()` |

エキスパンダ 0x44 のビット割り当て（`bsp_io_expander_pi4ioe_init` と
M5Unified `Power_Class.cpp` の突き合わせ）:

| bit | 名前 | 意味 |
|---|---|---|
| P7 | CHG_EN | **1 で充電許可**（active-high） |
| P5 | QC_EN | **0 で QC 有効**（active-low） |
| P4 | PWROFF | 1→0 パルス×3 で電源断 |
| P3 | USB5V_EN | USB-A ホスト給電 |
| P0 | WLAN_PWR_EN | C6 電源（`board_tab5.c` が使用） |
| P6 | 入力 | 充電/USB-C ステータス（0x0F で読む） |

EXT 5V だけは**もう一方の**エキスパンダ 0x43 の P2。

M5Unified の `setChargeCurrent()` がこの 2 ビットの意味を明かしています:
**0mA = CHG_EN off / 500mA = CHG_EN on + QC off / 1000mA = CHG_EN on + QC on**。
QC ピンは入力電流の段選択です。

### この端末固有の 2 つの制約

設計の大半はここから来ています。

1. **電源が入っているときしか充電しない。** M5 の公式ドキュメントに明記が
   あり、公式ファームも HAL init で CHG_EN を立てています。つまり
   **シャットダウンは安全側の既定ではない** — 充電器を挿したまま電源を切ると
   充電も止まります。
2. **6.0V を割ると保護がラッチし、復帰手順は「電池を抜いて本体をリセット」**。
   このファームで唯一、ユーザーが工具を出す羽目になる故障モードです。そこへ
   落ちる前に自分で電源を切ること、が本コンポーネントの最大の存在意義。

> 本作業の着手時点で、このファームは **CHG_EN を一度も立てていませんでした**
> (`board_tab5.c` が BSP と同じ `OUT_SET=0b00001001` を書いて P7 を low のまま
> にしていた)。つまり USB を挿しても充電されない状態でした。残量表示より先に
> 直すべきはこの 1 ビットです。

## 2. アーキテクチャ

内部 I2C（G31/G32）は **ui_tab5 が port 1** で作り `ui_tab5_i2c_bus()` で公開。
INA226 も両エキスパンダもここに乗るので、audio_tab5 (ES8388 @0x18 + SPK_EN
@0x43) と同じ相乗りです。ドックキーボードの port 0 (G0/G1) とは別物。

```
board_tab5_power_init()          早期ブート、一時バス
  └─ pwr_tab5_early_charge_on()  QC → 50ms → CHG_EN   ← 充電はここで始まる
ui_tab5_start() → tab5_ui_ready()
  └─ pwr_tab5_start()            所有タスク (1Hz) を起動
       ├─ INA226 サンプル
       ├─ pwr_gauge_step()       ← 純粋計算、ホストでテスト済
       ├─ ポリシー (上限充電 / ラダー / シャットダウン)
       └─ コールバック: notify / sample / shutdown
```

**単一オーナー**です。0x44 の OUT_SET への書き込みは全部 `exp_set_bit()` を
通り、mutex 下の read-modify-write。microlink の lifecycle_task で学んだ形と
同じ理由 — 出力レジスタ 1 本を 2 人が触ると、片方が意図しないビットを倒します
（ここでは C6 の電源が倒れる）。

**依存の向き**は `main → pwr_tab5 → ui_tab5` の一方通行。ステータスバーへ出す
ために ui_tab5 が pwr_tab5 を参照すると循環するので、電池は 1Hz の sample
コールバックで main に渡り、main が `ui_status_set_battery()` で押し込みます。
`ui_status_t` は plain int のまま（ui_tab5.h は電池コンポーネントを知らない）。

早期ブートで充電を入れるのは、UI（＝共有バス）の起動を待たないためです。
充電が画面の初期化に依存する理由は 1 つもありません。

## 3. ゲージ (`pwr_gauge.c`)

M5Unified の線形マップ（3.30–4.15V/セル）も ESPHome の線形マップ（6.0–8.23V）も
**端子電圧**を読みます。この端末はカメラ・Wi-Fi・バックライトで負荷が数百 mA
動くので、端子電圧そのままの % はスキャンを始めた瞬間に 8 ポイント落ちます。
それは % ではありません。信用できる順に 3 層:

### 3.1 IR 補正

INA226 は電圧と電流を同じノードで返すので、内部抵抗が**可観測**です。

```
V = OCV + I·R            (I は電池へ流れ込む向きが正)
```

忘却係数付き逐次最小二乗 (λ=0.998、1Hz で約 500 秒の記憶) が θ=[OCV, R] を
推定します。励起は端末が勝手に作る負荷ステップ（バックライト、カメラ、Wi-Fi）
で足ります。**能動的な摂動は入れません**。

ガードが 2 つ。回帰子 `[1, I]` は負荷が一定な間ずっと同じ方向を向くので、素の
RLS は励起されない方向で共分散 P を無限に膨らませます。そこで (a) P の対角を
上限で止め（ゲインの上界）、(b) 毎更新後に θ を物理的にあり得る範囲へクランプ
（R は 50–800mΩ）。どちらも安いし、どちらも**良いサンプルを悪い R に変えることは
ありません**。

保護ラダーが閾値にするのは θ[0]（遅い）ではなく、**瞬時の** `OCV = V − I·R`
です。電池がサグったら 1 サンプルで反応してほしいので。ADC ノイズだけは
τ=10 秒の EMA で落とします。

### 3.2 クーロンカウント

シャント電圧 LSB 2.5µV / 5mΩ = **0.5mA/LSB**。校正レジスタは**書きません**し
CURRENT/POWER レジスタも**読みません** — データシートのその経路はホスト側の
除算を省くためのもので、ここでは量子化（公式ファームの
`calibrate(0.005, 8.192)` は current LSB を 0.3mA へ切り上げます）と、シャント
読みと食い違い得る状態を 1 つ増やすだけです。生シャントは正確で、算術は
`raw × 5`（0.1mA 単位）だけ。

INA226 のオフセット誤差は最悪 ±2mA 相当 → 6 時間で 12mAh、2000mAh の 0.6%。

### 3.3 錨 (anchor)

積分のドリフトを消す 3 点:

| 錨 | 条件 | 効果 |
|---|---|---|
| 静止 | \|I\| < 50mA が 60 サンプル連続 | OCV テーブルから SoC を再設定 |
| 満充電 | CHG_EN on かつ V>8.10V かつ 0<I<100mA (≈C/20) が 60 サンプル | SoC=100%、**容量を学習** |
| 保存値 | 起動時、前回のクリーンシャットダウンで NVS に残した SoC | 積分の初期値（弱い錨。容量学習の基準脚にはしない） |

容量学習は「前回の錨からのクーロン ÷ その間の SoC 差 × 100」。SoC 差が 40 未満
の区間は**ノイズしか学習しない**ので捨てます。結果は 1000–3200mAh に
クランプし、半分ずつブレンド。学習値は NVS へ。

### 3.4 表示

生の SoC をそのまま出すとチラつくので:

- 3 秒に 1 ポイントまで
- **方向ゲート**: 放電中は上がらない、充電中は下がらない（推定器に理由が
  あっても、放電中に % が上がる表示は「壊れたゲージ」に見えます）
- 5 ポイント以上ずれたら、または錨が発火したらスナップ

残り時間は τ=5 分の電流 EMA から。2000mAh の端末では % より実用的です。

### 3.5 OCV テーブルは暫定

`s_ocv[]` は「健康な 2S Li-ion の一般形をセル×2 して、下端を M5 の公称
（満 8.23V → 停止 6.0V、約 6 時間）に寄せたもの」で、**NP-F550 の実測ではあり
ません**。§7 の較正手順で置き換えてください。

暫定でも運用に耐えるのは、(a) 保護ラダーがこのテーブル由来の % ではなく
**OCV のミリボルト**で閾値を切っていること、(b) 満充電の錨がテーブルと無関係に
クーロンから容量を学習し直すこと、の 2 点によります。

## 4. 保護ラダー

USB の有無に関わらず走ります。各段は「% または OCV のどちらか悪い方」で入り
ます — 冷えた起動直後は % が錨なしで当てにならない一方、電圧は常に正しいので。

| 段 | 閾値 (% / OCV) | 動作 |
|---|---|---|
| LOW | 25% / 7.35V | 通知、画面タイムアウトを 1/2 |
| SHED | 15% / 7.10V | USB-A (0x44 P3) と EXT 5V (0x43 P2) を停止、タイムアウト 1/3 |
| CRITICAL | 8% / 6.85V | 通知、タイムアウト 1/6 |
| SHUTDOWN | 4% / 6.60V | 猶予つき自動シャットダウン |

昇段は 5 サンプル連続、降段は 30 サンプル連続（フラップ防止）、SHUTDOWN だけ
10 サンプル連続。カメラ + Wi-Fi のバーストで誤射しないための多数決です。

**充電器があるときも減段しません。** 外部 5V を切り、画面を暗くして、充電器に
負荷との勝負をさせるのが「ほぼ空だが挿さっている」の正しい答えです。充電器が
禁じるのは最後の段だけ — §1 の制約 1 のせいで、充電中のシャットダウンは電池を
救うのではなく見殺しにします。

### シャットダウンの手順

1. 黒箱 (`term_lp_log(TERM_LP_CLASS_SYS, "battery", …)`) に理由と (OCV, V, %,
   mA) を 1 行。**最初に**書くのは、この後の掃除が失敗しても理由が残るように。
2. `mqjs_request_stop_all()` → 全アプリの `sys.onStop("battery")` が走る
   （ハンドラはウォッチドッグで囲まれているので、掃除がカウントダウンを
   止めることはない）。以後ランチャーと dev スロットの復活を止める。
3. ack、または猶予（既定 30 秒、`CONFIG_MQJS_TAB5_BATTERY_GRACE_S`）の満了で
   NVS に SoC を保存し、0x44 P4 を 3 回パルス。

カウントダウン中に充電器が現れたら**中止**します。

アプリ側は新 API を覚える必要がありません — 既存の `sys.onStop(reason)` に
`"battery"` が増えただけです。

## 5. 充電上限（寿命）

Li-ion を 100% で保持し続けるのが劣化の主因なので、100/90/80% を選べます。

- 停止: SoC ≥ limit → CHG_EN off（状態は `limited`）
- 再開: SoC ≤ limit − 5
- **最短滞在 120 秒**: CHG_EN の連打は IP2326 の再ネゴを誘発しかねない
- 「今回だけ満充電」(`power.fullOnce()`) は次の満充電到達まで上限を無視

> **実機で確かめること**: CHG_EN を落としたとき、USB 接続中でもシステムが
> 電池から給電されるなら、上限充電は電池をすり減らすだけの機能になります。
> その場合は「上限で停止」をやめ、通知のみに変えます。§8 の観測項目。

## 6. JS API と UI

```js
var b = power.battery();
// { ok, pct, state, mv, ma, ocv, mohm, mah, cap, eta, usb, charging,
//   limit, tier, raw, n }
```

`pct` と `eta` は不明なら -1。`state` は `unknown|none|discharging|charging|
full|limited`。`raw` はエキスパンダの入力レジスタ（bring-up 用）。

読み取りは全アプリに開放 — 残量は capability ではありません。**変更する側**
（`power.charge()` / `power.limit()` / `power.fullOnce()` / `power.off()` /
`power.sign()`）は `camera.scanQr` や `system.*` と同じく**システムアプリ専用**
で、居場所は `device_settings.js` の「バッテリー」画面です。

ステータスバーの電池アイコンはフォントグリフではなく LVGL の矩形 3 つで
描いています。ステータスバーのフォントは日本語サブセットで、電池の
コードポイントが残っている保証がないからです。色は状態を運びます
（充電中=青 / ≤15%=赤 / ≤30%=橙 / それ以外=緑）。**電池が無いときは何も
出しません** — 空の輪郭は「残量ゼロ」に読めて、事実と逆です。

## 7. 較正手順（実測 OCV テーブル）

```bash
# ブローカー側
mosquitto_sub -h <broker> -t 'esp32p4-mqjs/battery' -v > trace.log
```

1. 上限を 100% にして満充電（緑が消えるまで）
2. USB を抜き、`examples/battery_trace.js` を起動して放置（約 6 時間）
3. 自動シャットダウンしたらログを保存
4. `python tools/battery_fit.py trace.log` → `s_ocv[]` を印字
5. `components/pwr_tab5/pwr_gauge.c` に貼り、**ホストテストを再実行**
   （テーブルの単調性を検査します。放電の平坦部はノイズで簡単に崩れます）

fitter が報告する容量は「その走行で実際に取り出せた電荷」＝**使える容量**で、
ラベルの値ではありません。60% から始まったトレースは上位 60% に圧縮された
曲線を作るので、食わせないこと。

## 8. 検証状況

### 済み

- **ホストテスト** `components/pwr_tab5/host_test/test_gauge.c` — 7 項目
  （曲線の単調性と往復、IR 補正、静止/満充電の錨と容量学習、6 時間放電、
  電池なし、dt クランプ）。実行:
  ```bash
  wsl gcc -O2 -o /tmp/test_gauge components/pwr_tab5/host_test/test_gauge.c \
      components/pwr_tab5/pwr_gauge.c -I components/pwr_tab5 -lm && /tmp/test_gauge
  ```
  実測: R を 0.203Ω（真値 0.200）に収束、端子電圧の振れ 246mV に対し OCV は 67mV。
- **サボタージュ検証**（テストが本当に落ちることの確認）— 3 種、いずれも
  ちょうど 1 件失敗:

  | 壊した箇所 | 落ちたチェック |
  |---|---|
  | IR 補正を外す (`ocv = v`) | [2] IR compensation |
  | 満充電の錨から CHG_EN 条件を外す | [4] no CHG_EN, no full anchor |
  | dt クランプを外す | [7] 1h ギャップで 1000mAh 積分 |

- **ファームビルド** Tab5 構成で警告 0・エラー 0、bin 4.0MB（36% 空き）
- **PC ランナー** `run_pc` がスタブで `power.*` を返すこと、`device_settings.js`
  と `battery_trace.js` が構文・実行とも通ること
- **fitter の往復** 合成トレースから元のテーブルを ±12mV で復元

### 未検証（実機が要る）

**実機では一度も動かしていません。** 最初の実機セッションで確認する順序:

1. **電流の符号**。INA226 の向きはどこにも文書がなく、公式 UI は
   「current ≥ 0 なら充電」と扱っています。既定はそれに従い +1。逆なら
   `power.sign(-1)`（設定画面にボタンあり）または
   `CONFIG_MQJS_TAB5_BATTERY_INVERT_CURRENT=y`。
2. **CHG_EN が実際に充電を始めるか**（電流の符号反転と電圧上昇）
3. **CHG_EN=off + USB 接続時に放電するか** → §5 の分岐が決まる
4. **P6 の極性**（BSP は `usb_c_detect`、M5Unified は `CHG_STAT` と呼ぶ）。
   `power.battery().raw` の bit6 を挿抜で観察。現状は電流符号を主、P6 を従と
   して OR しています。
5. **満充電の錨**が本当に発火するか（IP2326 のテーパー特性次第）
6. **ラダーの誤射がないか**（カメラ + Wi-Fi のバースト中に段が上がらないこと）
7. **シャットダウンの一連**（黒箱の行 → onStop → 電源断 → 次回起動で
   `lastboot` に理由が残る）

## 9. 置いた既定値（要判断）

計画時に挙げた 3 つの判断待ちは、実機セッションを止めないよう既定を置いて
進めてあります。変えたければここだけ触れば足ります。

| 項目 | 既定 | 場所 |
|---|---|---|
| OCV テーブル | 一般形の暫定値（§3.5、§7 で置換） | `pwr_gauge.c` `s_ocv[]` |
| 充電上限 | **100%**（従来どおり）、設定で 90/80 | `pwr_tab5.c` `s_limit_pct` / NVS |
| シャットダウン | **6.60V または 4%、猶予 30 秒** | `T_DOWN_MV` / `CONFIG_MQJS_TAB5_BATTERY_GRACE_S` |
