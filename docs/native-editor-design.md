# 端末上のエディタとファイラ — ネイティブ化の設計

PC もブローカーも無しで、端末の上でスクリプトを書いて走らせる。そのための
エディタと、その足場になるファイラ／ファイルピッカーを**ネイティブ (C)** で
作る。`docs/filer-storage-design.md` が作った `fs_core` の上に載る。

---

## 1. 決まったこと (要約)

| | |
|---|---|
| ファイラ・エディタは **ネイティブ** | JS アプリではない。理由は §2 |
| ピッカーが**権限の入口**になる | アプリはボリューム全体ではなく 1 ファイルを受け取る (§4) |
| `edit_core` は**純 C99** | ホストで単体テストと fuzz。LVGL 依存は薄いプレゼンタに閉じる (§3) |
| **フラッシュ停止の対策は先送りする** | 先にエディタを作り、実使用で頻度を測ってから判断 (§6) |
| 編集中のスクリプトは **dev スロット**で走らせる | エディタは「ブローカー無しの push」なので役割が同じ (§3.4) |

---

## 2. なぜネイティブか

### 2.1 これらはアプリではなく、プラットフォームの一部

証拠が 2 つある。

**ファイル管理アプリが、ファイルを書く許可を求めていた。** 一般の OS で
ファイルマネージャは許可を*求める側*ではなく*与える側*（ファイルピッカー）
なので、`filer-storage-design.md` §7 の構図は層を 1 枚間違えていた。

**ブートストラップが循環していた。** 今のファイラを端末に入れるには
ブローカーが要る。ネットワークの無い場所で何かが壊れたとき、直す道具が
入っていない。エディタは「MQTT push の代わり」に欲しいものなのに、
入れるのに MQTT が要るのでは本末転倒になる。

### 2.2 「JS か C か」は正しい軸ではなかった

この repo には既に 3 段ある。

| 段 | 例 | 更新 | 権限 | worker |
|---|---|---|---|---|
| 組み込み JS システムアプリ | launcher, device_settings | **再フラッシュ** | `trusted_system` | 1 本消費 |
| push された JS アプリ | files (プロトタイプ) | 無線 | サンドボックス | 1 本消費 |
| ネイティブ C | ui_status, term_core, skk_core | **再フラッシュ** | 全権 | 消費しない |

**更新コストで見ると、組み込み JS とネイティブは同じ。** 「JS の方が更新が
楽」という理由は、これらを「ファームに同梱するインフラ」と決めた時点で消える。

そして本当の比較はこうなる:

- **A** = `edit_core`(C99) + LVGL プレゼンタ(C) + シェル(C)
- **B** = `edit_core`(C99) + LVGL プレゼンタ(C) + **JS バインディング層(C)** + JS シェル

どちらでもバッファと描画は C になる（256KB の移動 GC アリーナで毎キー
文字列を作り直す JS バッファは論外）。**B は A から層を減らす構成ではなく、
A に層を足す構成**で、差は「シェルを JS で書くためにバインディング層と
ワーカースロット 1 本を払うか」だけ。

### 2.3 スロットが足りない

`MQJS_MAX_WORKERS = 4`、slot 0 = 常駐ランチャー、slot 1 = dev。
**空きは 2 本しかない。**

エディタの操作ループは「編集 → 実行 → エラー → 該当行へ」で、この間
エディタと被編集スクリプトが同時に生きている必要がある。B なら
シェル 1 本 + 被編集 1 本で空きを使い切り、そこにピッカーが JS なら
3 本目が要って成立しない。A ならエディタは 0 本。

### 2.4 シェルが元を取るかの判定

> JS シェルが「C が持てない状態」か「ユーザが差し替えたいポリシー」を
> 持たないなら、それはシェルではなくバインディングの言い訳。

`ssh_vt.js` が元を取っているのは、どのホスト・何タブ・接続ダイアログという
**可変の構造**を持つから。エディタのシェルが持つのは「ハンドル 1 個と整数
数個」で、これに該当しない。しかもピッカーがネイティブになると、シェルの
仕事だった「開く」は C の呼び出しになり、**JS に残る仕事が無くなる**。

### 2.5 失うもの

**プラットフォームのドッグフーディング。**「JS ランタイムで実用アプリが
書ける」の証拠が、いちばん使うアプリ 2 本から消える。

ただしファイラの JS プロトタイプが見つけた欠落は具体的だった ── retain
スタックが 3 段しかないので階層を JS 側の `cwd` で持つ必要があった、
grant がボリューム単位で粗い、長い処理を逃がす口が無い。**これらは JS 層の
改善として残す**。エディタは理屈が通らない側（打鍵のホップは JS 層を
どう直しても消えない）。

## 3. 層の分け方

```
ネイティブ・エディタ  ネイティブ・ファイラ   ← LVGL プレゼンタ (C、薄い)
        |                    |
   edit_core (C99)      ファイルピッカー (C) ← 権限の入口
        |                    |
        +--------- fs_core ---------+        ← ボリューム登録簿・仮想パス
```

### 3.1 `edit_core` — 純 C99

`term_core` / `skk_core` / `ime_core` と同じ形。ESP-IDF のヘッダを含まず、
`run_pc` にリンクして ASAN + libFuzzer で叩ける。

持つもの: gap buffer、行インデックス、カーソル/選択/undo、
`view_rows()` が cell 行と dirty 範囲を返す、IME 合成文字列の差し込みフック、
構文エラー位置。

**公開関数は `(buf, len)` とインデックスだけを受け、内部ポインタを外に
出さない。** gap が動くのでプレゼンタが `char*` を保持したら即 UAF。
プレゼンタは無状態で、毎描画で `view_rows()` を引く。

### 3.2 プレゼンタ — 薄くて馬鹿な層

`edit_core` が出す cell 行と dirty 範囲を、`ui.cells` と同じ blit 経路で
貼るだけ。**LVGL オブジェクトを増やさない**（1 行 1 label は 720p で即死）。

注意: **`ui.cells` は既に PPA 経路**。グリフを内部 SRAM の A8 バッファ
`s_cells_a8` (17,280 B) に合成し、PPA blend で PSRAM のキャンバスへ入れ、
6 セル未満の run と PPA 失敗時だけ CPU にフォールバックする。「`ui.cells` を
使うが PPA は使わない」は成立しない。

`s_cells_a8` は JS の `ui.cells` と共有なので、エディタは**自前の
ステージングバッファ (内部 SRAM 17KB)** を持ち、PPA エンジンだけを共有する。
確保後の内部 SRAM largest が 40KB を切るなら諦めて共有し、専用ミューテックスで
直列化する。

### 3.3 タスク配置

`edit_task` を **core 1、UI タスクより 1 段高い優先度**で持つ。
打鍵 → `edit_core` → 行 relex → **ロック無しで**キャンバスバッファへ blit →
`lvgl_port` ロックを取って `invalidate_area(dirty rows)` → 即解放。
ロック保持は µs。

JS タスクは core 0 なので、**エディタは JS タスクに一切依存しない**。
他アプリが長い C 呼び出しで JS タスクを止めていても打てる。

### 3.4 実行は dev スロットへ

端末上エディタは「ブローカー無しで push する」ための代替経路で、dev スロットは
「push されたスクリプトを走らせる場所」。役割が同一なので同じ枠を使う。
こうすると編集/実行ループが**ユーザ用の空きスロットを 1 本も使わない**。

**dev スロットの自動再実行は、エディタ起点の実行では抑止する。**
dev は落ちると 1 秒後に再実行するので、構文エラーのたびに 1 秒周期の
再起動ループになる（実際に NUL バイト 1 個で観測した）。明示 stop が
再実行を抑止する機構は既にあるので、それを使う。

エラーの行/列は app manager からエディタの C コールバックで受ける
（JS API を新設しない）。

### 3.5 デバイス側に構文チェックの口が無い

エンジンは構文解析だけできるが、それをやっているのは**ホストツール**
`components/mqjs/tools/compile_task.c` だけ。デバイス側に binding が無いので
新規 C 作業になる。実行前とアイドル 1 秒後にだけ走らせ、毎打鍵はしない。

## 4. 権限 — ピッカーが入口

### 4.1 攻撃者モデル (先に明示)

| 相手 | 守るもの | 本気度 |
|---|---|---|
| 行儀の悪い JS アプリ | 他アプリのデータ、`apps/` の完全性 | **主戦場** |
| 敵対的な SD カード | `apps/` への無署名コード侵入 | **主戦場** |
| LAN 上のブローカー | 改竄は署名で不可。ロールバックは受容 | 低 |
| **物理アクセス** | download mode を持つ相手に flash 上の防御は演劇。**スコープ外** | — |
| ユーザの操作ミス | 誤削除・誤フォーマット (安全性であってセキュリティではない) | 中 |

守るのは「**署名鍵が承認したコードだけが署名済みアプリの顔で走る**」と
「**アプリ同士が互いのデータに触れない**」の 2 点だけ。

### 4.2 ピッカーは capability を返す

返すのは **grant id (不透明整数)**。パス文字列は表示用に添えるだけで権威では
ない ── パスを権威にすると、ピッカーを閉じた後もアプリが「名前を知っている
パス」に書ける ambient authority になる。

既存の grant テーブルに種別を足すだけでよく、**2 つの権限概念は作らない**:

```c
uint8_t kind;   /* SCOPE_SUBTREE | SCOPE_FILE | SCOPE_APPDIR */
uint8_t ops;    /* READ|WRITE|CREATE|DELETE|RENAME */
```

寿命判定は既存のまま流用する ── 発行時の worker+gen と `fsvol_epoch` を
**使うときに見比べるだけ**。失効コールバックもタイマーも要らない。

`SCOPE_FILE` は完全一致。save モードのピッカーは「まだ存在しないパス」に
`CREATE|WRITE` を出す。付与後に別の主体がそのファイルを rename したら
アプリは ENOENT を見る ── inode の無い FATFS/littlefs で追跡はしない。

### 4.3 アプリ私有ディレクトリ

`/internal/data/<app>` に**同意不要の暗黙 grant**を置く。読書アプリや
回路計算機が自分の記録を書く用途はこれで済み、同意画面に流れ込まない。

### 4.4 同意画面はネイティブへ移す

ピッカーがネイティブモーダルである以上、同意画面はその部分集合（パスを
固定し閲覧を殺しただけのダイアログ）で、C の増分はほぼゼロ。

決定的な理由が 1 つある: **ランチャーは JS 協調タスク上のアプリなので、
他アプリが長い C 呼び出しをしている間は同意画面を描けない。** 実際に
カタログ検証で 1.8 秒フリーズを観測した。ネイティブモーダルは UI タスクで
独立に動く。

### 4.5 provenance は「導出される事実」にする

ロンダリングを構造的に防ぐ唯一の方法は、provenance を**ファイル内の
フィールドにしない**こと。

```
SYSTEM … 組み込み (trusted_system)
SIGNED … crypto_sign_open が通った
LOCAL  … 署名が無い / 通らない (エディタ産)
```

SIGNED は検証結果から**毎回導出**する。LOCAL を SIGNED に見せるには鍵が要り、
**鍵は端末に置かない**（規則として明文化）。

エディタは `/internal/scripts/` に保存し、実行は dev スロットへ LOCAL として
投入する。`apps/` への昇格には `sys.install` を使わない（署名必須のまま
2 つの意味を持たせない）。

### 4.6 `apps/` 不変条件

`fs_core` のパス解決の一箇所に予約サブツリーとして実装済み
（`fs_reserved.c`、`filer-storage-design.md` 参照）。ネイティブファイラも
ピッカーもそこを通るので、「`apps/` を避ける」ことを覚えなくてよい。
覚えなければならない規則は、いつか誰かが忘れる。

## 5. JS API の移行

**破壊的変更は `feat/filer-storage` が main に入る前だけ無料。** マージ後に
変えるコストは桁が変わるので、まとめて適用する。

| API | 判定 | 理由 |
|---|---|---|
| `fs.volumes / list / stat / read` | 残す | 読み取り開放は既決 |
| `fs.mount` | **削る** | マウントは 150ms 級のブロッキング C 呼び出しで、JS から呼べると誰でも全アプリを止められる |
| `fs.unmount` | **削る** | 他アプリの grant を epoch 失効させられる = ワーカー間 DoS レバー |
| `fs.format` | **削る** | ファイラ専用。JS に残す用途が無い |
| `fs.request / release` | 残す・狭める | サブツリー grant はバルク操作アプリにだけ必要 |
| `fs.write / mkdir / remove / rename / copy` | 残す | 権限の**入口**が変わるだけで操作は必要 |
| `fs.pick(opts, cb)` | **新設** | 権限の主たる入口 |
| `/internal/data/<app>` | **新設** | 同意不要の逃がし弁 |
| `sys.fsConsent` + ランチャーの同意画面 | **削る → ネイティブモーダルへ** | §4.4 |
| `sys.store / install(name, src)` / カードカタログ | 残す (JS のまま) | 構造がデータ駆動で可変 = JS が元を取る側 |

`examples/files.js` は捨てず、**移行ゲート**として残す ── ネイティブ版が
同じ操作列で同じ結果を出すことを条件にする（`tools/tests/ime_diff.sh` と
同じ考え方）。

## 6. フラッシュ停止 — 測ったが、対策はしない

### 6.1 何が起きるか

フラッシュの program/erase 中、IDF はキャッシュを落とし、**もう一方のコアを
IRAM のスピンループに閉じ込める**。この間、flash の `.text` / `.rodata` が
読めない。影響を受けるのは:

- フォントの glyph_bitmap **1,492,265 B**（`.flash.rodata` 2,200,712 B の **68%**）
- SKK 辞書（mmap パーティション）
- ほぼ全部のコード

**実測: 両コア停止は core 1 のスループットを約 4 割削る**
（150 回の littlefs 書き込み中に core 1 が回せた CRC 回数 100 vs 162）。

**ただしこれは 150 回連続書き込みという意図的な酷使での値で、通常動作の値ではない。**
通常動作（Wi-Fi + Tailscale、打鍵なし、30 秒）を `flash_stall_meter` で測ると
停止は 120 回/秒・平均 59µs・最大 5.2ms・**壁時計の 0.7%** だった（§7）。回数が
多いのは、auto-suspend 無しでは**読みを含む全ての SPI1 ドライバ操作**がキャッシュを
落とすからで、大半は littlefs / NVS の読み。**「4 割」を XIP の根拠に使わないこと** ——
根拠になるのは §6.4 の「打鍵中に何回重なるか」だけ。

### 6.2 auto-suspend は採らない (実機で検証済み)

`SPI_FLASH_AUTO_SUSPEND` はキャッシュ停止そのものを消す。チップは
XMC-D (0x464018) で IDF の汎用ドライバが名指しで対応扱いにしている。

**3 構成を実機で測った:**

| 構成 | 結果 | core1 の CRC 回数 |
|---|---|---:|
| ON / 消去と同優先度 | **panic ループ** (Instruction access fault) | 154-162 |
| ON / 消去を高優先 | 破損なし。ただし **TWDT が繰り返し発火** | 127 |
| OFF | 安定 | 100 |

`TSUS_VAL_US` は 50 でも上限 100 でも、`AUTO_CHECK_SUSPEND_STATUS=y` を
足しても 1 番目は落ちた。**tSUS は原因ではない**（tSUS は resume の準備時間
なので、上げるほど次の suspend に追い越されやすくなる = 悪化方向）。

原因は IDF のドキュメントに書いてある:

> relies heavily on **strict timing** … you cannot use it in every situation,
> like **triggering interrupt very frequently (e.g., LCD flush, bluetooth, Wi-Fi)**
>
> Low-priority code … **should be forbidden from being executed** during erasing

Tab5 は MIPI-DSI の flush と SDIO の Wi-Fi を常時走らせている ── 名指しされた
2 つが両方。優先度を直せば破損は消えるが、消去が延びて core 0 が飢える。
**「消去中に走ってよいのは消去より高優先で短くて稀なコードだけ」という枠は、
連続的に描画するエディタと原理的に相容れない。**

### 6.3 残る道と、その値段

`SPIRAM_XIP_FROM_PSRAM` が唯一の残り
（`SPI_FLASH_CACHE_NO_DISABLE` の条件は auto-suspend か
`FETCH_INSTRUCTIONS && RODATA` のどちらか）。

ただし **XIP 単独は採ってはいけない**。IDF のこの条件は「コードと rodata が
PSRAM にあるなら flash のキャッシュ流量はゼロ」という仮定に立っているが、
mmap した辞書はその仮定を破る唯一の存在。auto-suspend 無しでこれを erase 中に
読むと、止まるのではなく**黙って壊れた値を受け取る**。

だから XIP は **jisyo の PSRAM コピーとセット**になる。値段:

| | |
|---|---:|
| 常駐 PSRAM (現状) | 5.7 MB |
| + XIP (.text + .rodata) | 約 4 MB |
| + jisyo 松 | 8.46 MB |
| + カメラ/QR のピーク | 約 9 MB |
| **= ピーク / 32MB** | **約 27 MB** |

加えて起動 +1.3 秒、命令フェッチが PSRAM 帯域に乗る（描画バッファ・編集
バッファと同じコントローラ）、そして「アロケーションもロードもゼロ」という
辞書設計の性質を手放す。

### 6.4 だから先送りする — この文書の中心的な決定

**先にエディタを作り、実使用で「打鍵中にフラッシュ書き込みが何回起きるか」を
測ってから、XIP をやるかどうか決める。**

理由: 停止が痛いのは**フラッシュ書き込みと打鍵が重なったとき**だけ。
エディタのオートセーブは「2 秒アイドル後」= 打っていない時にしか走らない
設計にする。そうすると残る書き込みは NVS のコミット、アプリのインストール、
ログの永続化で、どれも打鍵と重なる頻度は低い。

**12MB の PSRAM と 1.3 秒の起動時間を払って、めったに起きない停止を消す**こと
になりかねない。対策を先に作り込むと、必要のない代金を払う。

測り方: `--wrap` でフラッシュ操作を**タスク別に**数えるカウンタを入れ、
エディタを普通に使っている間に `edit_task` の打鍵経路が何回停止したかを見る。
ゼロに近ければこの工事は要らない。

### 6.5 それでも今から守る規則

対策はしないが、**後から対策できる形**にはしておく。打鍵経路では:

1. flash の program/erase をしない（直接も間接も）
2. `lvgl_port_lock` の保持下で blit / relex / `edit_core` を呼ばない
3. JS タスクへ同期呼び出しをしない（構文チェックも非同期）
4. I/O タスクへ同期待ちをしない
5. `malloc` / `free` をしない（起動時に PSRAM で確保、固定上限）
6. 内部 SRAM を新規確保しない（起動後の largest 61KB は SDIO/lwIP の分）
7. NVS を読まない

オートセーブは**アイドル駆動**（2 秒 or 100 編集）。`store.*` の遅延コミットには
**30 秒の上限**を置く ── 無期限の遅延はクラッシュをデータ損失に変換する
（`store.*` が watchdog reset に間に合わず消えた前例がある）。

## 7. 実測値 (2026-08-25, Tab5)

設計判断の根拠。推測と区別するために出所を残す。

| 項目 | 値 |
|---|---|
| Ed25519 検証 1 回 | **226 ms** (tweetnacl、HW アクセラレータ無し) |
| 両コア停止のコスト（150 回連続書き込みの酷使） | core 1 スループット **-38%** |
| 両コア停止（通常動作、30 秒、打鍵なし） | 3,605 回 / 合計 213ms / max 5.2ms / **壁時計の 0.7%**、83% が 64µs 未満 |
| SKK 変換 1 回 | 77 µs (設計文書、竹でも松でも同じ) |
| 辞書引き — mmap flash | **26 µs** avg / 179 µs max |
| 辞書引き — PSRAM コピー | **13 µs** avg / 146 µs max (+8.46MB, 起動 +1.1s) |
| `.flash.rodata` | 2,200,712 B (フォント 2 種で 68%) |
| PSRAM | **32 MB**。常駐 5.7MB / カメラ込みピーク 14.8MB |
| 内部 SRAM | 562 KB。実行時 free 117KB / largest 61KB |
| LVGL 描画バッファ | 内部 SRAM に 2 × 72,000 B |
| JS キャンバス | PSRAM 1,716,480 B |
| `s_cells_a8` | 内部 SRAM 17,280 B |
| キャンバス実寸 | 1280 × 632 |
| littlefs | 1 MB。アプリ 7 本で 205 KB |

**推測を書かない。** この文書は 2 度、推測で判断を誤りかけた ──
Ed25519 を「5〜30ms」と見積もって実際は 226ms、辞書引きの PSRAM 化を
「2.5µs」と見積もって実際は 13µs。数字は測ってから書く。

## 8. 順序

1. **ピッカー**（ネイティブモーダル、grant を返す） ── 土台
2. **ファイラ**（ピッカーの上の操作層）。`examples/files.js` を移行ゲートに
3. **`edit_core`**（純 C99、ホストで ASAN + fuzz）
4. **プレゼンタと `edit_task`**
5. **ベンチマーク** ── 打鍵→表示の p99、および打鍵中のフラッシュ操作回数

## 9. やらないと決めたこと

- **`SPI_FLASH_AUTO_SUSPEND`**: 実機で検証して却下 (§6.2)。**再挑戦しないこと** ──
  ドキュメントが名指しで我々の構成を除外している
- **jisyo の PSRAM コピー（性能目的）**: 実測 13µs しか縮まない (§7)。
  XIP の前提条件としてのみ意味がある
- **XIP 単独**: jisyo の mmap 読みが erase 中のチップに当たる (§6.3)
- **エディタのバッファを JS で持つ**: 移動 GC アリーナで毎キー文字列を
  作り直すのは論外
- **エディタのシェルを JS にする**: 持つ状態が無い = バインディングの言い訳 (§2.4)
- **打鍵経路で PPA を独立に叩く**: `ui.cells` が既に PPA 経路 (§3.2)
