# 実装計画 — 自律・並列開発の運用

`docs/native-editor-design.md`（外形）と `docs/native-editor-spec.md`（仕様）を
実装に落とすための**進め方**の文書。何を作るかではなく、**誰が・どう回すか**を
決める。

方針: **役割を事前に決めた複数エージェントを並列に走らせ、opus の監督が全工程を
見る。実装と検証のループを回して品質を上げる。人の手は原則として借りない。**

---

## 1. なぜループが品質を上げるのか（今日の実例）

この方針は正しい。ただし**「検証が失敗できる」ことが条件**で、それが無いループは
品質を上げずに「通った気」だけを増やす。今日それが両方向で起きた。

**効いた例。** 予約サブツリーのホストテストは、書いた後に境界判定を素朴な
`strncmp` へ差し替え、`/internal/appsfoo` が誤検出されることを確認してから
戻した。テストが**名指しした欠陥で実際に落ちる**ことを見た。

**効かなかった例。** auto-suspend の受け入れ試験はデータの CRC を見ていて、
3 構成すべてで `mismatches=0` だった。壊れていたのは**命令フェッチ**で、
データだけ見る試験なら PASS と誤判定して出荷していた。panic したから気づいた。

だから本計画の中心規則は 1 つ。

> **検証物は、それが名指しする欠陥を注入して落ちることを見せるまで、
> 通ったことにしない。** そして「何を見ていないか」を検証物自身に書く。

## 2. 役割（事前に固定する）

| 役 | model | 担当 | 触ってよい範囲 |
|---|---|---|---|
| **監督** | opus | 全工程・統合・マージ・**デバイスの唯一の所有者**・未決事項の判断 | 全部 |
| **core 実装** | opus | `edit_core`（純 C99、gap buffer、行索引、undo、字句） | `components/edit_core/` |
| **fs 実装** | opus | `fs_picker`、grant の `kind`/`ops` 拡張、ネイティブ・ファイラ | `components/fs_core/`, `components/fs_picker/` |
| **UI 実装** | sonnet | LVGL プレゼンタ、`ui_tab5` への 3 本の追加、`edit_task` | `components/ui_tab5/` |
| **計測実装** | sonnet | `sys.perf()`、ヒストグラム、`--wrap` 各種、回帰の数値比較 | `main/`, 計測系 |
| **敵対的検証** | opus | 各成果物のテストを**壊して確かめる**。仕様との突き合わせ | 読み取り + `*/pc_test/` |
| **仕様保守** | fable | 仕様の更新、未決台帳、実測値の反映 | `docs/` |

model の割り当ての理由: **境界判定・並行性・セキュリティ境界を含むものは opus**
（今日、prefix 判定の 1 文字と、タスクをまたぐロック前提の崩れが、どちらも
静かな欠陥になりかけた）。配線と反復作業は sonnet。仕様の文章は fable。

**役割の外に出ない。** 今日、調査を頼んだエージェントが自分のフォークに
再委任して報告経路が二重になった。担当範囲と報告先は起動時に固定する。

## 3. 並列に切れるもの / 切れないもの

```
edit_core ──┐
            ├── edit_task + プレゼンタ ── エディタ
ui_tab5 ────┘
fs_picker ── ネイティブ・ファイラ
計測 (M0) ── 独立。今すぐ回せる
```

- **独立**: `edit_core`（ESP-IDF に触らない）、`fs_picker`、計測。3 本を同時に走らせられる
- **合流点**: プレゼンタは `edit_core` の `view_rows` 契約が決まらないと書けない。
  **ヘッダを先に凍結**して、両者が同じヘッダに向かって書く
- **直列**: 実機での検証はデバイスが 1 台しか無い（§5）

---

## 4. ループの単位

各エージェントは**この順序を 1 周とする**。周を跨いで仕掛かりを残さない。

1. 仕様の該当節を読む（推測しない。曖昧なら止めて監督へ）
2. ホストで動く形に実装（純 C99 の部分は `run_pc` にリンクできること）
3. **ホストテストを書き、欠陥を注入して落ちることを確認**し、戻して緑を確認
4. ASAN + UBSan で通す。`edit_core` は libFuzzer も
5. NUL バイト掃除（§7）
6. 監督へ報告: 変更点 / **検証したこと と 理屈で言っているだけのこと の区別** /
   仕様と食い違った点
7. 監督がレビューし、必要なら敵対的検証へ回し、worktree のブランチをマージ

**「検証したこと」と「たぶん大丈夫」を混ぜて報告しない。** 今日いちばん
信頼できた報告は、その 2 つを見出しで分けていた。

## 5. 排他資源 — デバイスは 1 台しかない

**Tab5 は 1 台、COM8 は 1 本。並列エージェントが各自でフラッシュすることは
できない。**

- **デバイスの所有者は監督だけ。** 他のエージェントは `idf.py flash` /
  `esptool write-flash` / `erase-region` / COM8 の open を**禁止**
- 実装エージェントはホストで検証し、実機検証は監督にキューイングする
- 実機の 1 回の焼き込みで**複数の検証をまとめて**回す（焼き込みは 30 秒〜1 分、
  松の辞書込みなら +35 秒）
- worktree で作業する場合、`sdkconfig.tab5*` は gitignore なので本チェックアウト
  からコピーが要る。コピー後に `CONFIG_ESP_HOSTED_SDIO_HOST_INTERFACE=y` と
  `CONFIG_ESP_HOSTED_CP_TARGET_ESP32C6=y` が残っていることを**必ず確認**する
  （新しい worktree の初回 configure で managed component の symbol が落ちた前例）

## 6. 自律の限界 — 人の手が要るのはどこか

「人の手は借りない」を最大化するが、**物理的に不可能な箇所がある**。計画に
明記しておかないと、そこで黙って止まる。

| 要る作業 | なぜ自律化できないか | 緩和 |
|---|---|---|
| **画面を打鍵する** | エージェントはキーを発生させられない。M0 の `typing` カウンタ、打鍵→表示の p99、IME の体感はすべてこれ待ち | **`mqjs_post_key()` を叩くテストフックを入れる**。機能ループは自律化できる。ただし ISR→I2C の実経路を通らないので、**レイテンシの数値は実キーでしか取れない** |
| **画面を見る** | 描画の正しさ、文字化け、レイアウト崩れ | セル配列のスナップショット比較で大半は代替できる（`term_core` の pc_test と同じ手） |
| **SD を抜き差しする** | 取り外し検出、grant 失効、未フォーマット状態 | 代替不可。まとめて 1 回で試す |
| **フラッシュを焼く** | 監督が持つ（§5） | — |

**運用**: 人手が要る検証は**溜めてバッチにする**。「1 つ終わるたびに人を呼ぶ」を
やると自律の意味が無い。監督が「人の手待ち」キューを持ち、たまったところで
一括して依頼する。

## 7. 今日踏んだ落とし穴（標準の規則にする）

| 落とし穴 | 規則 |
|---|---|
| 機械編集で **NUL バイト**が文字列リテラルに混入（2 回）。`SyntaxError: unexpected end of string` で dev スロットが 1 秒周期の再起動ループ | ファイルを書いたら**必ず NUL 走査**。報告に結果を書く |
| **CRLF** でアンカー一致が失敗（worktree のマージ後にチェックアウトで変換される） | パッチは行末を正規化してから当てる |
| エージェントが**アイドル通知だけ送って本文を送らない**（3 回） | 報告は本文で送る。アイドルは報告ではない |
| **推測の数字**で判断を誤りかけた（Ed25519 を 5〜30ms→実測 226ms、辞書 PSRAM 化を 2.5µs→実測 13µs） | 数字は実測か「測る必要がある」のどちらか。推測値を仕様に書かない |
| ドキュメントが「READ DOCS FIRST」と書いているのに読まずに焼いた | 挙動を変える Kconfig は、ドキュメントを読んでから触る |
| 計測器自身のバグ（コアごとに別のサイクルカウンタを引き算して max 10.18 秒） | 計測器にも**妥当性の下限・上限**を持たせ、外れ値は黙って捨てず**捨てた数を数える** |

## 8. マイルストーンと担当

| M | 内容 | 担当 | 進める条件 | そこで測れるもの |
|---|---|---|---|---|
| **M0** | 計測の土台（`--wrap` 停止カウンタ、`sys.perf()`） | 計測 | — | 停止の頻度・分布。**実装済み・実測開始済み** |
| M1 | `edit_core` の骨格（バッファ・行索引・カーソル） | core | ヘッダ凍結 | ホストのみ |
| M2 | `fs_picker` + grant 拡張 | fs | 仕様 §A | ホスト + 実機 |
| M3 | プレゼンタ + `edit_task` | UI | M1 のヘッダ | 打鍵→表示 |
| M4 | undo / 検索 / 字句 | core | M1 | — |
| M5 | ネイティブ・ファイラ | fs | M2 | `filer_diff.sh` |
| M6 | 構文チェック + 行ジャンプ + dev スロット実行 | core + 計測 | M3 | 端対端 |
| **判断** | XIP をやるか | 監督 | M0 の `typing` 実測 | — |

## 9. 監督が持つもの

- **未決台帳**（仕様 §E）。エージェントが勝手に決めない。決めたら台帳に記録
- **人の手待ちキュー**（§6）
- **デバイス**（§5）
- **マージ**。worktree のブランチを読んでからマージする。今日の 2 件は
  サボタージュ確認まで済んでいたので通した
- **止める判断**。auto-suspend は 3 構成測って捨てた。**捨てたものを記録し、
  再挑戦しない**（設計文書 §9）

## 10. 最初の一手

M0 は実装済みで、ベースラインが取れている（30 秒で停止 3,605 回、合計 213ms =
壁時計の 0.7%、平均 59µs、最大 5.2ms）。**残るのは `typing` カウンタで、
これは人が打鍵しないと 0 のままになる。**

したがって最初の一手は 2 本並行:

1. **人の手**: Tab5 で `ssh_vt` を開いてしばらく打つ → `typing` の実測 →
   XIP の判断が閉じる
2. **自律**: M1（`edit_core`）と M2（`fs_picker`）を並列で起動。どちらも
   ホストで完結するのでデバイスを待たない
