# キーボードと日本語入力の共通化 (設計)

打鍵の意味付けは `kbd_core` に集約済みですが、**入力面が 1 つだけそこに乗って
おらず**、**IME の見た目と操作がアプリごとの実装**になっています。この文書は
その 2 つを同じ場所へ下ろすための設計です。実装前の設計であり、まだ 1 行も
書いていません。

## 1. なぜ今か

`components/kbd_core/include/kbd_core.h` の冒頭が、この問題の前例をそのまま
書いています。

> Two surfaces feed the same apps: the Tab5 keyboard dock (kbd_tab5) and the
> on-screen keyboard / control bar (ui_tab5). Before this component each had
> its own idea of what Ctrl+C or an arrow key should put on the wire, so the
> same intent reached apps as different bytes.

同じことが今度は IME で起きています。`ssh_vt.js` / `skk_test.js` /
`reading.js` の 3 本が、それぞれ独自に「IME をどう開くか・どう切り替えるか・
preedit をどこに描くか・確定をどこへ流すか」を書いています。3 本目
(`reading.js`, 2026-07-29) を書いた時点で、これは重複ではなく**欠けている層**
だと判断しました。

## 2. 現状の地図

| 入力面 | 打鍵の出口 | `kbd_core` | IME |
|---|---|---|---|
| ドック (A164) | `mqjs_post_key` → JS | ○ | アプリ実装 |
| オンスクリーン kbd + 制御バー | `mqjs_post_key` → JS | ○ | アプリ実装 |
| **ウィジェット `field`** | **`lv_textarea` へ直行** | **×** | **不可能** |

`field` だけが素の LVGL キーボードです。ツリー全体で `lv_keyboard_create` は
`components/ui_tab5/ui_widgets.cpp` の 1 箇所だけで、`lv_group` /
`lv_indev` のキーパッド結線はどこにもありません。コードから読み取れる帰結:

- **ドックの物理キーは `field` に入りません。** 出口が `mqjs_post_key` しか
  なく、フォーカス中の textarea へ渡す経路が存在しない (実機未確認、コード上は
  明らか)。
- `field_focus_cb` は `s_hw_kb` を見ないので、**ドック装着中でもオンスクリーン
  キーボードが出ます**。手元に物理キーがあるのに画面を叩かせている。
- その高さは 400px 固定。横向き (キャンバス 632px) では画面の大半を占め、
  `ui_tab5_set_landscape` が畳み直す対象にも入っていません。
- 制御バーも修飾キー LED も IME も、この面には一切効きません。

一方 IME 側は、C が「エンジン」(`skk_core`) と「フロート窓の描画」
(`ui_overlay` / `ovl_window`) を持ち、**その間の全部**をアプリが持っています:

- `openIme()` — 辞書 open と、失敗を恒久ラッチしてよい条件
- `imeToggle()` — 「あ」トークンの意味、`enable`/`reset`/`save`、告知
- `imeConsumed()` — ステータス bitmask の展開 (COMMIT/MODE/PREEDIT/CANDS/SEL)
- `imeFloat()` — アンカーの決め方と表示条件
- モード表示 (かな/カナ/▽/▼)
- **キーを渡す順序** — `rotate` と `ime` は skk より前、ESC と矢印は skk より後

最後の 1 行が曲者で、`tools/ssh_vt_imetest.sh` はこの順序だけを見張るために
存在します。3 本のアプリが同じ罠を各自で踏まないという保証は、今はありません。

## 3. 提案 — IME を `kbd_core` と同じ高さへ下ろす

```
        ┌──────────────┐
        │  skk_core    │  変換エンジン (純ロジック・REQUIRES 無し)
        └──────┬───────┘
               │
   ┌───────────┴────────────┐
   │  ime_core (新設)        │  セッション方針・状態・キーを渡す順序
   │   + フロート窓とモード表示 │  (描画は既存の ui_overlay を呼ぶ)
   └───────────┬────────────┘
               │  確定文字列 / 素通しキー
   ┌───────────┴────────────┐
   │  kbd_core → 各入力面      │
   └───────────┬────────────┘
        ┌──────┴──────┐
        │             │
   widget field    JS アプリ (ui.onKey)
```

`skk_core` は REQUIRES がゼロの純ロジックで、ホスト gcc でもビルドされます。
`ui_tab5` はすでに `kbd_core` に依存しているので、**層の向きは壊れません**。

アプリから見た変化は 1 つだけです: **IME が有効な間、`ui.onKey` に届くのは
IME を通り抜けたキーと、確定した文字列**になる。preedit も候補も届かない
(C が描くので描く必要がない)。`ssh_vt.js` は確定文字列をそのまま
`ssh.write()` へ流せばよく、上に並べた 6 項目を全部捨てられます。

`field` は同じ経路にぶら下げます。フォーカス時に素の `lv_keyboard` ではなく
プラットフォーム側のキーボード (kbd_core backed、ドック対応、制御バーつき) を
上げ、出てきた文字列を textarea へ入れる。これで **全アプリの全 `field` で
日本語が打て**、ドックが効き、横向きでも畳み直され、`reading.js` の
キャンバス迂回は不要になって削除できます。

## 4. 守らなければならない既存の挙動

移設で壊してはいけないもの。すべて実機かホスト台本で裏の取れている挙動です。

1. **ESC と矢印は skk より後**。▽ が開いている間、skk はこれを `TOK_SWALLOW`
   で飲む (preedit はカーソル位置に描かれるので、カーソルだけ動くと取り残される)。
   先に取ると「変換をやめたいだけの ESC」で編集や画面が飛ぶ。
2. **`"\x00ime"` と `"\x00rotate"` は skk より前**。
3. **preedit を確定前に外へ出さない**。リモートのシェルへ漏らさない。
4. **辞書 open の失敗を恒久ラッチしない**。`skk_dict.bin` は gitignore 対象で、
   クリーンビルドのファームには埋め込みが無い = 実際に起きる。ラッチすると
   辞書を焼いた後もアプリ再起動まで直らない。
5. **フロート窓は edge-triggered**。中央固定はハイライトが動かず手応えが消える
   (実機で却下済み)。
6. **確定は bracketed paste で囲まない** (ssh_vt)。囲むと vim の insert 中に
   paste が入り切りされて逆に壊れる。
7. IME オフ (`skk.save()`) とアプリ停止で学習を書き戻す。

`tools/ssh_vt_imetest.sh` の台本は、移設後は **`ime_core` のホストテスト**へ
移すのが筋です (`skk_core` と同じくホスト gcc で回る層になるので)。

## 6. モード表示をやめて、見た目に溶かす

今アプリが持っている「モード表示」は、実は **2 つの別の問題**を 1 つのウィジェット
に押し込んだものです。分けると片方は消え、もう片方はアプリの画面から出ていきます。

### 6.1 変換中の状態 → preedit そのものの見た目

▽ (読みを打っている) / 送り仮名 / ▼ (候補を選んでいる) は、**preedit が画面に
出ている間だけ**意味を持ちます。別の場所に札を出すのではなく、preedit の描き方で
表すのが素直です。IME として一般的な作法でもあります。

| 状態 | 表現 |
|---|---|
| かな/カナ をそのまま打っている | 装飾なし (打った端から確定して消える) |
| ▽ 読み入力中 | 下線 + 淡い背景 = 「まだ入力の途中」 |
| 送り仮名 | 同じ preedit の**中で**送り部分だけ濃さを変える |
| ▼ 候補選択中 | アクセント背景 (候補窓が同時に出ている) |

これで **`~` `*` `v` の記号が要らなくなります**。今の ssh_vt のモードセルは
`"  >JA"` `"  vJA"` という代用字で、▽▼ が等幅フォントに無いから記号を諦めた
結果でした ([`examples/ssh_vt.js`](../examples/ssh_vt.js) の `MODE_LBL`)。フロート窓は
C が UI フォントで描くので、記号を戻すことも**そもそも記号をやめること**もできます。

**API 含意**: 塗り分けには preedit を 1 本の文字列ではなく **span の並び**で
渡す必要があります。そして **後段でのパースは不可能**です — 推測ではなく
`build_preedit()` ([`components/skk_core/skk_kana.c`](../components/skk_core/skk_kana.c))
がこう組んでいるからです:

| モード | 構成 |
|---|---|
| ▽ 読み | `▽`(U+25BD) + reading + 未変換ローマ字 |
| ▽ 送り | `▽` + reading + **`*`** + okuri + 未変換ローマ字 |
| ▼ 選択 | `▼`(U+25BC) + 候補 + okuri (**区切り記号なし**) |
| かな/カナ | 未変換ローマ字のみ |

▼ のとき候補と送り仮名は**区切りなしで連結**されるので、境界は文字列を
いくら眺めても出てきません。長さを知っているのは `skk_t` だけです。

したがってアクセサは **`ime_core` ではなく `skk_core` に置きます**。しかも
「同じ規則をもう一度書く」のではなく、**`build_preedit()` が組み立てながら
境界を記録する** (数行) 形にします。合成規則が 1 か所に留まり、装飾を変えたく
なっても触るのはそこだけです。`ime_core` はそれを素通しするだけになります。

(この文書の初版は「`ime_core` にアクセサを足す」と書いていましたが、それだと
合成規則が 2 か所になります。上流に置くのが正しい。)

### 6.2 非変換時のモード → 制御バーの「あ」キーの面

英数 / かな / カナ は preedit が無いときの状態なので、6.1 では表せません。ただし
**表示専用の場所は要りません** — その状態を切り替えるボタンが既に常時見えている
からです。制御バーの「あ」キーの**面そのもの**を `あ / ア / A` と変えれば、
操作するものと状態を見るものが同じになります。

これは C 側で完結します (制御バーは `ui_tab5` の持ち物)。結果として
**アプリの画面からモード表示が消え**、ssh_vt はタブバー右端の 4 セルを取り戻し、
`drawMode()` と `MODE_LBL` / `MODE_BG` は削除できます。

### 6.3 実装の制約 (2026-07-30 調査)

フロートを C から出すこと自体は追加の配管が要りません。`js_ui_overlay` は
lines と items を `\2` 区切りで 1 本の文字列に詰めて `ui_post_bg` に所有権を
渡しているだけなので、C 側で同じ文字列を組んで同じ関数を呼べば済みます
(⚠️ 渡すのは必ずヒープ。スタック配列を渡して UI タスクにスタックアドレスを
free させ、無関係な確保でヒープが壊れた前例がコメントに残っています)。

**問題は塗り分けの手段です。**

- `CONFIG_LV_USE_SPAN is not set` — LVGL のリッチテキスト (`lv_spangroup`)
  はこのファームに入っていません。
- `lv_label_set_recolor()` と `LV_TEXT_FLAG_RECOLOR` は使えます。つまり
  **1 つのラベルの中で span ごとに前景色を変えることはできます**
  (`#RRGGBB …#` 記法。色文字列は C 側が span から組み立てる)。
- **下線と背景は span 単位では出せません。** §6.1 の表は「下線 + 淡い背景」
  「アクセント背景」と書いていますが、そのままでは実装できません。

選択肢は 3 つ:

| 案 | 得るもの | 代償 |
|---|---|---|
| 前景色だけで区別 (recolor) | 設定変更なし、コード最小 | 下線・背景は使えない。淡い色は屋外で見えるか要実機確認 |
| `CONFIG_LV_USE_SPAN=y` | 仕様どおり | フラッシュ増、`sdkconfig.tab5` 変更、未使用機能の持ち込み |
| span ごとに子ラベル | 下線も背景も自由 | 自前レイアウト。フロートの幅計算とクランプを書き直す |

**推奨は前景色だけで始めること。** 色の可読性はどのみち実機で見ないと
決まらず (§6.3)、そこで足りないと分かってから子ラベルへ進めば、要らない
LVGL 機能を抱え込まずに済みます。

### 6.4 決めないこと

具体的な色は **ここでは決めません**。この
プロジェクトでは UI の感触を実機で確かめてから確定させる方針で、選択窓の

## 7. 配線 (決定済み)

§6 でモード表示が C 側へ移った結果、**JS に出るものがほぼ無くなりました**。
mode も preedit も候補もモード定数も JS を跨ぎません。`skk_preedit_spans()` も
C↔C です。アプリから見える新 API は 2 つだけです。

```js
ui.ime(1);            /* canvas アプリの opt-in。field は自動 */
ui.caret(x, y, h);    /* 変換中の文字列をどこへ出すか */
/* 確定した日本語は既存の ui.onKey に普通の文字列として届く */
```

`ui.caret` だけは C が知り得ないので残ります (フロートは「目線を動かさない」
ために存在するので、固定位置に出すのは本末転倒)。とはいえアプリの負担は
**減ります**: 今は打鍵が消費されるたびに 6 フィールドの spec を組んで
`ui.overlay` を呼んでいるのが、カーソルが動いたときだけの数値 3 つになります。

フロート自体は **アプリの `ui.overlay` 呼び出しから C の `ui_post` へ**移ります。
新しい配管はゼロで、既存の `UI_CMD_OVERLAY` の発行元が変わるだけです。ssh_vt が
`OVL_IME = 0` で押さえていたスロットはアプリに返ります。

### フックは `mqjs_post_key()` 1 か所

両方の入力面が既にここへ集まっており、この関数は既に純粋な「JS へ投げる」係では
ありません (アイドル時計の更新とスリープ復帰キーの握り潰しをしている)。

置き場所は **復帰キーの握り潰しの後、`fg->key_used` チェックの前**です。

- **後**: 画面を起こしただけのキーで変換を始めない
- **前**: 現状のこの行が §2 の根っこだから —

```c
if (!s_event_queue || !fg->used || !fg->key_used || !utf8)
    return;   /* ui.onKey を登録していないアプリでは、打鍵はここで死ぬ */
```

`launcher` や `reading` のようなウィジェット専用アプリは `ui.onKey` を呼ばない
ので、**打鍵はここで捨てられています**。「ドックの物理キーが `field` に入らない」
の正体はこれでした。IME とシンク振り分け (フォーカス中の textarea か JS アプリか)
をこの手前へ置けば、**I3 の目玉が別作業ではなく構造的に片付きます**。

```
ドック ──┐
         ├─> mqjs_post_key: ime_feed() ─┬─ 確定/素通り → シンク
画面kbd ─┘                              │    ├─ フォーカス中の field → textarea
                                        │    └─ それ以外 → 既存の JS キュー
                                        └─ view dirty → ui_post(OVERLAY / 「あ」キー面)
```

### ⚠️ 最初の opt-in より前に片付けること

W2 (`1e8a6af`) までは `ui.ime()` を呼ぶアプリが 1 本も無く、`ime_used` が
立たないので `mqjs_ime_feed()` は最初の分岐で `IME_PASS` へ抜けます。つまり
以下は**どちらも今は到達しません**。逆に言えば、**最初に opt-in するアプリを
入れた瞬間に両方とも生きます**。

1. **共有 `ime_t` の排他。** `ime_core.h` は「1 つの `ime_t` は 1 タスク所有」
   を前提にしていますが、`mqjs_post_key()` は **LVGL タスク**
   (オンスクリーンキーボード、自動回転の `"\0rotate"`) と**ドックの kbd
   タスク** (`kbd_tab5.c`) の両方から呼ばれ、`ui.ime()` は mqjs タスクで
   走ります。ドックで打ちながら回転する、は普通に起きます。

2. **学習の書き戻しが入力タスクで走る。** `mqjs_ime_feed()` は「あ」で IME を
   切った縁で `skk_mru_flush()` を呼びますが、これは `malloc` + `mkdir` +
   `fopen`/`fwrite` の同期 littlefs I/O です。LVGL タスクで走れば描画が、
   ドックの kbd タスクで走ればキースキャンが、その間止まります。打鍵ごとでは
   ないとはいえ、入力経路で同期 I/O を踏むのは筋が悪い。

どちらも「排他を足す」で済む話ではありません。**IME の状態遷移と I/O を
どのタスクで走らせるか**という設計判断で、W3 でフロート描画 (LVGL タスクの
持ち物) を足すときに一緒に決めるのが自然です。microlink の
`lifecycle_task` + コマンドキュー (単一所有者に寄せて、どの文脈からも
post するだけにする) が、このプロジェクトで既に一度出した答えです。

### §5 の API 案との関係

- **`skk.*` をアプリ面から降ろす**: §6 で完全化 (定数まで含めて内部へ)。I1 と同時。
- **トークンを `ui.onKey` の第 2 引数に**: **緊急度が下がりました**。重要だったのは
  「アプリが順序を間違えると IME が壊れる」からで、その保証は `ime_core` が構造で
  持ちました。扱いにくさは残るので価値はありますが、I1 と同時にやる必然性は無い。
- **`ui.keyboard` の command/query 分離**、**`ui.onResize`**: IME とは独立。

## 8. 未決 (実装前に決めること)

### 8.1 IME をどこまで C が持つか

- **案 A: C が全部持つ** — アプリは確定文字列だけ受ける。UX が全アプリで完全に
  揃い、アプリのコードは最小。ただし ssh_vt の細かい方針 (§4 の 1〜7) を C の
  中で表現しきる必要があり、アプリ固有の例外を入れる余地が減る。
- **案 B: C は共通部品、方針はアプリ** — 今より薄い共通化。移行は楽だが、
  「同じ UX」という目的は半分しか達成できない。

**推奨は A。** §4 の 7 項目はどれもアプリ固有ではなく、3 本とも同じ答えを
持つべきものだから (それが今バラバラに書かれていることが問題)。

### 8.2 canvas アプリの opt-in

`field` は常に IME つきでよいが、キャンバスアプリは端末なら欲しく、ゲームなら
要らない。`ui.ime(1)` のような明示 opt-in にするか、`ui.keyboard()` の mode に
畳み込むか。**opt-in を推奨** (既存アプリの挙動を変えないため)。

### 8.3 英語 (ASCII) の扱い

「あ」で IME をオフにしたときの経路は、今も IME を通らない素通しなので変更
不要です。ただし **`field` の英字入力は現状 LVGL のキーボードのレイアウトに
依存**しており、プラットフォーム側へ移すとレイアウトが変わります (記号の位置が
変わる)。移行時に見た目が変わることを許容するか、`ui_tab5` 側のキーマップを
先に見直すか。
